# CatelliteV2F (Nim)

Nim で書いた独立系 VRM → FBX コンバータです。元の Blender / Python パイプライン
（`CatelliteV2F_old`）の出力品質を、**Blender・bpy・VRM-Addon・
Cats-Blender-Plugin を一切使わずに**再現します。すべての工程を最初から実装
し直しています。変換コアは Nim 標準ライブラリのみに依存し、ウィンドウ版 GUI
のみ nimact（`G:\nimact`）を使用します。

## ビルド

```sh
nimble build
```

以下は等価です。

```sh
nim c -d:release --app:gui --mm:arc -o:catellitev2f.exe src/catellitev2f.nim
```

nimact は `nimble.paths` 経由で `--path:"G:\nimact\src"` を追加し、コピーではなく
常に現在のソースを直接コンパイルします。nimact 以外に依存はありません。
nimble パッケージも、C ライブラリも、Python も使いません。

以下の 2 つのフラグは `config.nims` に書いています。`nimble build` はどちらも
渡せず、コマンドラインに書かないと壊れたバイナリを黙って作ってしまうためです。

**`--app:gui`** — Windows GUI サブシステムでリンクします。exe をダブルクリック
しても、窓の背後に残るコンソールが開かなくなります。致命的エラーは出力先が
無いので nimact の `messageBox` で表示します。

**`--mm:arc`** — 見た目のためではなく、必須です。GUI は変換をワーカースレッド
で実行するため、全スレッドが同一ヒープを共有する必要があります。共有されな
いと、ワーカー側で確保した領域は他のスレッドが読む時点ですでに消えています。
ツールチェーンで nimact が 3 つのマネージャを実測した結果（ワーカーが
`seq[string]` を作り、`uint` ハンドル経由で返す形）は次の通りです。

| `--mm` | 結果 |
| --- | --- |
| `arc` | 正しく読み戻せる |
| `refc` | **初回読み取りで SIGSEGV** — スレッド終了時にワーカーのページが解放される |
| `orc` | 読み戻しはできるが、ヒープはスレッドローカルと明記されている |

`--threads:on` で単一の共有・ロック保護ヒープを実装しているのは `arc` です。
ここで `refc` が 3 つのうち**最悪**であることは、よくある誤解と正反対です。
「修正」されないよう、`config.nims` にはその根拠をコメントとして残しています。

これは実際に踏みました。変換は結果をワーカー内に保持してファイルへ
直接書き出すため、`refc` のままでもすべての変換が成功し、正しい FBX が
出力されます。クラッシュには「ワーカーが確保した領域を UI スレッド側へ
返す」形が必要で、その形がそれまで出てこなかったため、潜伏していました。

## 使い方

```sh
catellitev2f.exe input.vrm output.fbx   # 直接変換
catellitev2f.exe                       # GUI を起動
```

GUI では元 VRM と出力 FBX を選ぶか、`.vrm` / `.glb` をウィンドウにドロップします。
どちらの場合も出力パスはソースの隣の `<名前>.fbx` として自動決定され、上書き
できます。変換はワーカースレッド上で進捗バー、現在ステージとファイル名、
ログペイン付きで実行されます。FBX の書き出しが完了すると **Open folder** が
表示されます。`Cancel` はステージ間で反映され、変換中にウィンドウを閉じると
書きかけのファイルを捨てる前に確認します。

## 出力物

コンバータは FBX の隣に次を出力します。

- `<名前>.fbx` — モデル本体。
- `<名前>.fbm\` — 全テクスチャを PNG として書き出します（Blender の FBX
  エクスポートに倣った構成）。FBX は `Video/Content` に画像を埋め込みますが、
  Unity をはじめ多くのツールはディスク上の画像を参照し埋め込み側を無視するため、
  テクスチャ付きの状態で読み込むにはこのフォルダが必須です。

## ファイル構成

| ファイル | 役割 |
| --- | --- |
| `src/catellitev2f.nim` | CLI エントリポイント。引数なしなら GUI を起動。 |
| `src/gui.nim` | ウィンドウ版フロントエンド。nimact の GUI ツールキット製。 |
| `src/appicon.nim` | ウィンドウアイコン（タイトルバー・Alt-Tab）。exe リソースから読込。 |
| `icon.ico` | アイコンの原寸データ。`icon.rc` + `icon.res` として exe に埋め込まれます。 |
| `src/core/m3.nim` | Vec / Mat / Quat / Euler の演算と Blender のボーン基底ヘルパ。 |
| `src/core/glb.nim` | JSON DOM、GLB / VRM コンテナ読み取り、アクセサ読み取り。 |
| `src/core/fbxw.nim` | バイナリ FBX ライタ（ノード・プロパティ・zlib・オフセット・フッタ）。 |
| `src/convert.nim` | シーン構築：ボーン、メッシュ、viseme、視線追跡、T-pose、マテリアル。 |
| `src/fbxexport.nim` | Blender のエクスポートに倣った要素・接続の出力。 |

## アイコン

`icon.ico`（256×256 / 32 bpp）は、Windows がアイコンを 2 箇所に保持する都合上、
両方へ入っています。

| 置き場所 | 設定方法 | 見える場所 |
| --- | --- | --- |
| exe のリソース | `config.nims` の `--passL:"icon.res"` | Explorer、タスクバーボタン、ファイルのプロパティ |
| ウィンドウ | `src/appicon.nim`、起動時に `WM_SETICON` | タイトルバー、Alt-Tab |

ウィンドウ側に必要だったのは、nimact がウィンドウクラスを `hIcon` なしで登録
し、`newGuiApp` にアイコン引数もないためです。このままでは exe に正しいアイコン
が入っていてもタイトルバーには Windows の既定アイコンが出ます。

前半の「exe への埋め込み」は `--win32icon` なら 1 行で済むところですが、
`config.nims` では許可されるオプションが限られており `--win32icon` は拒否され
ます（`.nimble` からも渡せないため、`nimble build` はアイコンなしの exe を黙って
作ってしまいます）。そこで `icon.rc` で `windres` に `icon.res` を作らせ、
`config.nims` に書ける `--passL` でリンクしています。

`icon.res` はビルド成果物としてツリーに残してあります。`windres` が入っていない
環境でも、そのままチェックアウトしてリンクできるようにするためです。
`icon.ico` を変更した場合は `nimble build` するだけで、
`catellitev2f.nimble` の `before build` フックが `.ico` より新しい場合に作り直
します。手動実行は `tools\build_icon.ps1` で、同じ処理です。`windres` が無い
場合は**失敗させずに警告**します（アイコンが多少古いだけでビルドを落とす価値は
ありません）。

実行時にはアイコンをディスク上のファイルではなく**動作中の exe 自身のリソース**
から読み込むため、コピー先やインストール先にファイルを隣接させる必要がなく、
カレントディレクトリにも依存しません。

## パイプライン

1. GLB / VRM コンテナと内部の glTF JSON を解析（VRM 0.x **および** 1.x MToon）。
2. スキンのジョイントから骨組みを構築。ヒューマノイド名の対応表、Cats の名前
   正規化とリネーム規則、ダミールートの除去、upper-chest の併合（消えたボーンの
   ウェイトは吸収したボーンへ転送）。
3. Cats のエディットモード整形を適用。頭部を正す、ボーンの末端を子ボーンの頭へ
   吸着する、腰を脚と脊椎の間に 33% で置く、垂直な膝を前へずらす、
   退化したボーンを延長する。Blender は head / tail が変わるたびにボーンのフレームを
   作り直すので、ここでも roll を保存しています。
4. プリミティブごとにメッシュを構築：頂点、ループ（glTF のインデックスバッファに
   ポリゴンの区切りは無いので、`TRIANGLES` では 3 個の連続値として扱います）、
   ループごとの法線 / UV エッジ、スキンウェイト、シェイプキー
   （移動量がゼロのターゲットは Blender と同じく削除）。最後にシェイプキーを
   Blender の疎な表現——移動した頂点インデックスの一覧と、それに対する 3 座標
   ずつ——へ書き換えるので、viseme のコストは実際に動かす頂点数だけになり、
   メッシュ全体のコピーが不要です。
5. Cats の viseme シェイプ（`vrc.v_*`、`vrc.lowerlid_*`）。
6. Cats の視線追跡：`Eye_L` / `Eye_R` ボーンと、`LeftEye` / `RightEye` からの
   頂点グループコピー。
7. VRM-Addon のチェーンアルゴリズム（右手 → 右指 → 右親指 → 各指 → 右脚 →
   左腕 → …）に従う推定ヒューマノイド T-pose を、メッシュとシェイプキーをそれ
   に従って変形させながら Bind ポーズ（rest pose）に焼き込む。
8. 元スクリプトの Spine / Chest / Neck のエディットボーン処理。
9. FBX ドキュメントの出力：ヘッダ + SceneInfo、GlobalSettings、Definitions、
   Objects、Connections、Takes。

UV は出力時に V 軸で反転します（`v → 1−v`）。glTF の原点は左下、FBX は左上
だからです。これが無いと、カットアウトを使った面（liltoon の髪や眉マスク）が
すべて誤ったテクセルをサンプルして消えます。

シェイプキーのデルタは絶対座標ではなく、**ベースメッシュからのオフセット**とし
て書き出します。Blender の疎な `ShapeChannel` はデルタを格納する場所なので、
ここに絶対座標を書くと顔の変形が二重になります。

テクスチャフォルダの配置は Blender に合わせています。`<出力>\<出力名>.fbm\<ファイル>.png`。

## ボーンのローカル軸（解決済み）

このファイルの以前の版には、ここに「既知のブロッカー」が載っていました。ジョイント
位置がすべて正しいのに Unity で骨格が崩れる、というもので、原因は骨バインド行列
の 3x3 成分が 127 本中 114 本程度で反転していたことでした。原因は 2 つあり、
どちらも解決しています。

**1. ボーンの基底が不正だった。** Blender の `EditBone` フレームを再現するには
`vec_roll_to_mat3` が必要ですが、これは VRM-Addon や Cats-Blender-Plugin 側では
なく Blender 本体の C コードです（`source/blender/blenkernel/intern/armature.cc`
の `vec_roll_to_mat3_normalized`）。現在は −Y に近い場合のフォールバックを含め、
`src/core/m3.nim` の `boneBasis` にそのまま実装しています。これにより完全一致
するボーンは 9/123 から 120/123 になりました。

**2. `Lcl Translation` / `Lcl Rotation` を休息ポーズから書いていた。** Unity は
骨格をノードプロパティ（`Lcl *`）から組み立て、`BindPose` からは組み立てません。
そのため、ローカル回転が誤った基底で出力されたボーンは、`BindPose` が正しくても
腕が折れてしまいます。`Lcl Rotation` を `localRest.col().transposed` から出力す
るようにしたところ、Unity 経路の不一致は 68 ノードから 18 ノードへ減り、
`Left/Right` の shoulder・arm・elbow は完全に一致しました。

修正後の実測：腕は完全に水平（0.00°）、BindPose は 127 中 126 が完全一致、
`vrchat.py` のレポートも参照 FBX と同一です。

要素ごとの構造差分では、**81 要素だけが相違**し、いずれもボーンの
`Lcl Scaling` です。

### 既知の相違（VRChat に影響しないもの）

- **81 本のボーンの `Lcl Scaling`。** Blender は行列チェーンで float32 の誤差を
  蓄積するため、123 本中 81 本がスケール `1 ± 3e-5` となり、エクスポートが
  このプロパティを書きます。こちらのボーンスケールは厳密に `1` に分解される
  ため、このプロパティは出力しません（Unity はローカルスケール未指定時を 1 と
  みなします）。ボーン以外のモデル——`Armature` と 3 つのメッシュ——だけは
  両方のファイルで `Lcl Scaling = (100, 100, 100)` です。
- **`Left` / `Right wrist` のバインド行列。** 1 軸で 4.84° ずれています。
  ボーンの位置と向きは一致しており、フレームの roll だけが異なります。
- **頂点順序。** Blender のインポータは `Face` と `Hair001` の最終ブロックで
  異なる頂点順序になります。点集合としては同一です。
- **`LeftEye` / `RightEye` のボーン頭部**が Blender の位置から 7 mm ずれています。
  Cats が `Eye_L` / `Eye_R` を作ったあとに元の目ボーンを動かすためです。
  VRChat は `Eye_L` / `Eye_R` で視線を追跡し、これらは完全一致するのでアバター
  には影響しません。
- **`Hips` の頭部位置**が 3.6 mm ずれています。Cats が腰の `head.x` と `head.z`
  しか設定していないためです。
- **`vrc.v_*` のインデックス数**が 1 〜 91 個違います（総数 66,742 対 66,592、
  +0.2%）。差分はすべて 1e-5 m 以下で、Blender のシェイプキー保存における
  float32 の丸めが原因です。`vrc.v_pp` は Blender が 1,389 頂点動かすところ
  1,461 頂点動かします。見た目の変形は同じです。
- **オブジェクト ID。** Blender は Python のランダム化された `hash()` から FBX の
  オブジェクト ID を導出します。こちらは決定的な FNV-1a ハッシュを使うため、
  ID は設計上異なります。
- **`Creator` 文字列**が Blender の代わりに `CatelliteV2F (Nim) - 1.0.0` です。
- 3 つのメッシュ `Model` オブジェクトの出力順（`Face, Body, Hair` 対
  `Body, Face, Hair`）。見た目には影響しません。
